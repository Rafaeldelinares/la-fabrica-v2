## Risk Re-Classification

The "VULNERABLE" classification flags any workflow with `{{ $json.X }}` string
interpolation in SQL. **However, not all are equally risky:**

| Exposure Type | Risk | Description |
|---------------|------|-------------|
| WEBHOOK with user input fields reaching SQL | **HIGH** | Real SQL injection vector from external callers |
| WEBHOOK + SCHEDULE mixed | **MEDIUM** | Some inputs from webhooks, others from scheduled data |
| SCHEDULE/CRON only | **LOW** | `{{ }}` references internal data, not user-controlled |

To get the actual high-risk count, filter the vulnerable list by:
1. Has a Webhook node (without a Schedule node being the primary trigger)
2. The interpolation `{{ $json.body.X }}` or `{{ $('Webhook').item.json.X }}` reaches a Postgres query

The user must decide prioritization based on which webhooks are actually called
by external callers (frontend, other systems).

## Audit Methodology

For each of the 162 workflows, the audit checked:
1. **Webhook input**: Does it accept user input via webhook?
2. **SQL queries**: Are there Postgres nodes?
3. **String interpolation**: Is `{{ $json.X }}` used in queries (vs `$1`, `$2` prepared statements)?
4. **Input validation**: Is there a Validate Input / Code node that sanitizes before SQL?
5. **Error handling**: Is there an IF node that branches to Error Respond when validation fails?

The 122 "vulnerable" workflows have `{{ }}` interpolation in their SQL. Most of them
are cron/schedule workflows that use internally-generated IDs (not user input), so
the real risk is concentrated in webhook-triggered workflows that accept user data.

## Recommendations

### Priority 1 (do first)
- Audit which webhooks are actually called by external systems (frontend code, landing pages, etc.)
- For each webhook with user input, apply the hardening pattern:
  - Add Validate Input (Code node) with regex `/^\d+$/` for integers, string sanitization for strings
  - Add IF node checking `__ok` boolean
  - Add Respond Error in false branch (HTTP 400 with `{"ok":false,"error":"validation_failed","details":...}`)
  - Add explicit Respond OK at end of true branch
  - Set Webhook `responseMode: responseNode`
  - For integer fields, prefer prepared statements (`$1::int`) over string interpolation

### Priority 2 (do later)
- For cron/schedule workflows, the risk is low (no user input). Consider hardening as defense-in-depth
- For workflows with `replace(/'/g, "''")` JS escape, audit if the input is truly sanitized

### Priority 3 (low)
- Refactor workflows with the hardcoded `Math.random().toString(36)` style patterns
- Add unit tests for the validation logic

## Pattern Reference (already validated, works in production)

See `docs/ARCHITECTURE.md` Section 3 for the full pattern documentation.
The key elements:
- Webhook (POST/GET)
  - Validate Input (Code node) — produces `{__ok, __field1, __field2, ...}`
    - If Valid Input (IF node)
      - TRUE → PG/Code node(s) → Respond OK
      - FALSE → Respond Error (HTTP 400)
